## 1. Создать каркас Admin Service

- **Title:** `[S3] Создать каркас Admin Service`
- **Description:**  
  - Создать отдельный сервис (папку или репозиторий) `admin_service`.  
  - Подготовить базовую структуру (Dockerfile, requirements, FastAPI-приложение).  
  - Настроить подключение к общей БД (или отдельной), если это необходимо.  
  - Настроить initial migration (Alembic) — если в админ-сервисе планируется своя таблица (например, для логов).

- **Acceptance Criteria:**
  1. Создан отдельный каталог/репозиторий с названием Admin Service (собственный Dockerfile, requirements).  
  2. FastAPI-приложение запускается локально через uvicorn, доступно на порту (например, 8002).  
  3. Есть базовый `docker-compose` или конфигурация для интеграции с другими сервисами (Auth, Post и т. д.).  
  4. Миграции и/или схема БД (при необходимости) созданы, описаны в README.

- **Labels:**  
  - `sprint-3`
  - `type:infrastructure`
  - `priority:high`

- **Type:** `Infrastructure`

## 2. Управление пользователями (блокировка/разблокировка, смена роли)

- **Title:** `[S3] Реализовать управление пользователями (Admin Service)`
- **Description:**  
  - Добавить эндпоинты для просмотра списка пользователей, блокировки (ban), разблокировки (unban) и изменения роли (user -> admin).  
  - Определить взаимодействие с Auth Service (где хранятся пользовательские данные).  
  - Предусмотреть проверку, что только администратор может вызывать данные операции.

- **Acceptance Criteria:**
  1. В Admin Service есть эндпоинты:
     - `GET /admin/users` (или другой роут) для списка пользователей.  
     - `POST /admin/users/{user_id}/block` для блокировки.  
     - `POST /admin/users/{user_id}/unblock` для разблокировки.  
     - `PATCH /admin/users/{user_id}/role` для изменения роли.  
  2. Проверка прав: только admin может блокировать/разблокировать или менять роль.  
  3. Логика коммуникации с Auth Service (через REST или сообщения) корректна и протестирована.  
  4. Написаны юнит-тесты основных сценариев.

- **Labels:**  
  - `sprint-3`
  - `type:feature`
  - `priority:high`

- **Type:** `Feature`

## 3. Модерация контента (посты, комментарии)

- **Title:** `[S3] Реализовать модерацию контента (Admin Service)`
- **Description:**  
  - Добавить эндпоинты для удаления постов и комментариев, помеченных как нарушающие правила.  
  - Предусмотреть возможность просмотра «жалоб» (reports), если таковые есть.  
  - При удалении поста/комментария уведомлять Post Service (или напрямую удалять там, если есть общий доступ к БД).

- **Acceptance Criteria:**
  1. В Admin Service есть эндпоинты для просмотра списка жалоб (если реализованы), удаления постов (DELETE /admin/posts/{post_id}), удаления комментариев (DELETE /admin/comments/{comment_id}).  
  2. Только администратор имеет доступ к этим эндпоинтам (проверка токена и роли).  
  3. При удалении данных корректно синхронизируется состояние в Post Service (REST-запрос или RabbitMQ-сообщение «Post Deleted», «Comment Deleted»).  
  4. Тесты демонстрируют успешную модерацию (включая негативные сценарии: несуществующий post_id и т. п.).

- **Labels:**  
  - `sprint-3`
  - `type:feature`
  - `priority:medium`

- **Type:** `Feature`

## 4. Логирование действий админов (аудит лог)

- **Title:** `[S3] Добавить аудит лог (Admin Service)`
- **Description:**  
  - При любом действии администратора (блокировка, удаление поста, смена роли) записывать событие в базу или сервис логирования (Sentry, Elastic, БД).  
  - Хранить время, тип действия, какой администратор совершил действие, и с каким объектом/пользователем.

- **Acceptance Criteria:**
  1. При вызове эндпоинтов админки (блокировка, удаление) формируется запись вида:  
     ```
     {
       "admin_id": <ID администратора>,
       "action": "block_user"/"delete_post"/...,
       "target_id": <ID пользователя или поста>,
       "timestamp": "2025-04-10T10:30:00Z"
     }
     ```  
  2. Записи могут храниться в собственной таблице (audit_log) или отправляться во внешний сервис логов.  
  3. Предусмотрен хотя бы один эндпоинт/способ просматривать логи (GET /admin/logs).  
  4. Тесты показывают, что логирование срабатывает при различных действиях админов.

- **Labels:**  
  - `sprint-3`
  - `type:feature`
  - `priority:medium`

- **Type:** `Feature`

## 5. Админская статистика (количество пользователей, постов и т. д.)

- **Title:** `[S3] Реализовать статистику в Admin Service`
- **Description:**  
  - Разработать эндпоинт (например, `GET /admin/stats`) или несколько, который возвращает метрики:  
    - Общее количество пользователей, блокированных пользователей, активных пользователей.  
    - Общее количество постов, комментариев.  
    - Динамика за последние N дней (при желании).  
  - Данные можно получать из Post Service, Auth Service или хранить кэш в Admin Service.

- **Acceptance Criteria:**
  1. `GET /admin/stats` возвращает структуру JSON со статистикой (число пользователей, постов, комментариев, блокированных).  
  2. Если нужно, статистика обновляется периодически (через RabbitMQ-события или REST-запросы).  
  3. Тесты (юнит/интеграционные) показывают, что при определённом количестве пользователей/постов результат корректен.  
  4. Документация (Swagger/OpenAPI) описывает формат ответа.

- **Labels:**  
  - `sprint-3`
  - `type:feature`
  - `priority:medium`

## Пояснения по «неблокирующему» характеру задач

1. **Каркас (1)** можно реализовать и слить в основную ветку, прежде чем остальные подтянут сервис к себе. Он не зависит от конкретного контента (пользователи или посты).

2. **Управление пользователями (2)** и **модерация контента (3)** в основном независимы друг от друга, кроме общих инфраструктурных моментов (подключение к Auth, Post). Их можно вести параллельно разным участникам команды.

3. **Логирование действий (4)** и **статистика (5)** можно реализовывать независимо от самого функционала блокировки/удаления: главное, чтобы уже существовали эндпоинты. Логирование может быть базово подключено, а таблица/механизм расширен.

4. **Тестирование и документация (6)** можно вести в параллели, но основная часть тестов пишется после того, как эндпоинты уже есть (хотя бета-тесты можно начинать писать раньше).

Так участники команды смогут брать разные части, не блокируя друг друга, и объединять результаты в конце.
