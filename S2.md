## 1. Разделение монолита и подготовка базовой структуры микросервисов

- **Title:** `[S2] Разделить проект на микросервисы (базовая структура)`
- **Description:**  
  - Создать отдельные директории (или репозитории) для будущих сервисов (Auth, Post, Subscription и т. д.).  
  - Актуализировать/скопировать базовые файлы (Dockerfile, docker-compose.yml, requirements) в каждом сервисе.  
  - Решить, как будут передаваться `.env` и конфигурации (pydantic-settings) в разные службы.  
  - При необходимости настроить монорепозиторий или несколько репозиториев (обсудить подход в команде).

- **Acceptance Criteria:**
  1. Существуют отдельные каталоги (или репозитории) для каждого микросервиса.  
  2. docker-compose.yml (или набор .yaml-файлов) запускает несколько сервисов (Auth, Post и т. д.) + общие компоненты (БД, брокер сообщений).  
  3. Базовая структура каталогов, зависимостей и конфигурационных файлов подготовлена для каждого сервиса.  
  4. Документация/README обновлены с описанием, как запустить все сервисы вместе.

- **Labels:**  
  - `sprint-2`
  - `type:infrastructure`
  - `priority:high`

- **Type:** `Infrastructure`

## 2. Auth Service

- **Title:** `[S2] Создать микросервис Auth (подтверждение email, восстановление пароля)`
- **Description:**  
  - В отдельном сервисе Auth реализовать логику регистрации и авторизации, вынесенную из монолита.  
  - Добавить функционал подтверждения email (отправка ссылки/кода).  
  - Добавить эндпоинт восстановления пароля (сброс и смена через email).  
  - Описать эндпоинты и модели в OpenAPI/Swagger.

- **Acceptance Criteria:**
  1. Auth Service умеет регистрировать новых пользователей (POST: `/register`) и авторизовывать существующих (POST: `/login`).  
  2. Предусмотрен механизм отправки email для подтверждения (после регистрации) и сброса пароля (SMTP или внешний сервис).  
  3. При подтверждении аккаунта меняется флаг `is_active` (или подобный) у пользователя.  
  4. Endpoints задокументированы (Swagger/OpenAPI), протестированы (юнит/интеграционные тесты).

- **Labels:**  
  - `sprint-2`
  - `type:feature`
  - `priority:high`

- **Type:** `Feature`

## 3. Post Service (Комментарии и лайки)

- **Title:** `[S2] Создать микросервис Post (комментарии, лайки, загрузка изображений)`
- **Description:**  
  - Вынести CRUD по постам из монолита в отдельный микросервис Post.  
  - Реализовать возможность добавлять **комментарии** к постам (CRUD).  
  - Реализовать функционал **лайков** (счётчик лайков, проверка, кто уже ставил лайк).  
  - Добавить опциональную загрузку изображений (например, через S3/MinIO).

- **Acceptance Criteria:**
  1. Post Service (FastAPI + своя БД/схема) обеспечивает создание, редактирование и удаление постов.  
  2. Комментарии и лайки хранятся в таблицах (comments, likes) и связаны с соответствующими постами/пользователями.  
  3. Эндпоинты для комментариев (POST, GET, PATCH/PUT, DELETE) и лайков (POST/DELETE) протестированы.  
  4. Если реализуется загрузка изображений, должно быть показано (в Swagger/README) как загружать и получать их.

- **Labels:**  
  - `sprint-2`
  - `type:feature`
  - `priority:high`

- **Type:** `Feature`

## 4. Subscription Service

- **Title:** `[S2] Создать микросервис Subscription (подписка, лента)`
- **Description:**  
  - В новом сервисе реализовать логику подписки на пользователей (follow), а также отписки (unfollow).  
  - Реализовать хранение подписок: таблица `subscriptions` (user_id, follower_id).  
  - Эндпоинты для:  
    - Подписки на пользователя: `POST /subscribe/{user_id}`  
    - Отписки: `DELETE /unsubscribe/{user_id}`  
    - Получения списка подписок/подписчиков (GET: `/subscriptions` или аналог).  
  - Сформировать «ленту» из последних постов подписанных пользователей (запрос к Post Service по нужным ID).

- **Acceptance Criteria:**
  1. Subscription Service запускается отдельно, взаимодействуя с Auth (для проверки авторизованного пользователя) и Post (для получения постов).  
  2. Создана таблица (или модель) `subscriptions`, в которой хранится информация о том, кто на кого подписан.  
  3. Эндпоинты подписки, отписки и получения ленты работают и задокументированы.  
  4. Добавлены базовые тесты (юнит, интеграционные) на операции подписки и формирование ленты.

- **Labels:**  
  - `sprint-2`
  - `type:feature`
  - `priority:medium`

- **Type:** `Feature`

## 5. Интеграция сервисов (RabbitMQ + FastStream)

- **Title:** `[S2] Настроить RabbitMQ и событийную интеграцию между сервисами`
- **Description:**  
  - Добавить контейнер RabbitMQ в docker-compose (или отдельном YAML).  
  - Подключить FastStream (или аналог) в Auth, Post, Subscription для обмена событиями:  
    - Auth отправляет событие «User Registered» при регистрации.  
    - Post отправляет «Post Created» при создании поста.  
    - Subscription реагирует на события (например, «New User» для подписок).  
  - Проверить, что сервисы корректно обмениваются событиями без «ручных» запросов.

- **Acceptance Criteria:**
  1. RabbitMQ запущен в Docker, доступен сервисам.  
  2. Auth, Post и Subscription сервисы публикуют/слушают нужные события через FastStream.  
  3. Пример: при регистрации нового пользователя (в Auth) событие «User Registered» отправляется, и Subscription может реагировать (создавать какие-то дефолтные настройки или просто логировать).  
  4. Лог/мониторинг событий показывает, что обмен сообщениями происходит без ошибок.

- **Labels:**  
  - `sprint-2`
  - `type:infrastructure`
  - `priority:medium`

- **Type:** `Infrastructure`

## 6. Интеграционные тесты между сервисами

- **Title:** `[S2] Реализовать интеграционные тесты (Auth, Post, Subscription)`
- **Description:**  
  - Создать набор тестов, которые будут проверять полный сценарий:  
    1. Регистрация пользователя в Auth Service.  
    2. Создание поста (Post Service) от имени созданного пользователя.  
    3. Подписка другого пользователя (Subscription Service) и проверка, что он видит посты первого.  
  - При желании добавить тесты «с негативными сценариями» (ошибки авторизации, запросы без токена, неверные данные).

- **Acceptance Criteria:**
  1. Запуск тестов (через Pytest или иной фреймворк) поднимает тестовое окружение (docker-compose) со всеми микросервисами (Auth, Post, Subscription, RabbitMQ).  
  2. Тесты проверяют базовые сценарии (регистрация -> создание поста -> подписка -> отображение ленты).  
  3. Все тесты проходят без критических ошибок. В случае багов есть отчёт/лог с деталями.

- **Labels:**  
  - `sprint-2`
  - `type:testing`
  - `priority:high`

- **Type:** `Testing`

### Пример дополнительных лейблов

- `type:bug` — используется для ошибок.  
- `type:enhancement` — улучшения или доработки существующего функционала.  
- `type:docs` — задачи, связанные с документацией.  
- `priority:low/medium/high` — степень приоритета.  
- `status:in-progress` — статус, когда задача в активной работе.  

---

Таким образом, во втором спринте (S2) ключевые задачи сконцентрированы на **выделении микросервисов** (Auth, Post, Subscription), **интеграции** через брокер сообщений (RabbitMQ) и **проверке работы** всего комплекса сервисов посредством **интеграционных тестов**.
